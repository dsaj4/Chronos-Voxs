# AGENT.md

## Purpose

This file is the collaboration contract for Chronos-Vox.

Read it before starting implementation work, especially when multiple agents or engineers work in parallel.

The project is currently in a contract-first stage. The immediate goal is to keep the semantic pipeline stable while allowing parallel work on normalization, claim extraction, aggregation, publishing, and the frontend workspace.

## Product Direction

Chronos-Vox is a real-comment semantic analysis workspace, not a generic sentiment dashboard.

The canonical pipeline is:

`RawComment -> NormalizedComment -> Claim -> Viewpoint -> Storyline -> ForecastBundle`

Core product rules:

- `RawComment -> NormalizedComment` must be deterministic.
- `NormalizedComment -> Claim` must be a replaceable module. The first implementation uses LLMs.
- `Viewpoint` and `Storyline` display labels, titles, and summaries must be generated by LLMs for readability.
- `Viewpoint` and `Storyline` structural grouping must not depend purely on LLM judgment.
- Forecasting is real-time only on published storyline time series. Heavy data processing remains offline.
- The frontend must consume a published bundle and must not reconstruct core semantic objects in the loader.

## Important Directories

- `docs/core/`: product and architecture intent. Change rarely and only with explicit alignment.
- `docs/plans/`: implementation plans, sequencing, and milestone docs.
- `docs/adr/`: architecture decisions, especially contract or model-boundary changes.
- `backend/src/chronos_vox/normalize/`: deterministic preprocessing from raw comments to normalized comments.
- `backend/src/chronos_vox/claims/`: candidate span generation, LLM claim extraction, validation, caching, and audit.
- `backend/src/chronos_vox/viewpoints/`: deterministic viewpoint grouping logic.
- `backend/src/chronos_vox/storylines/`: deterministic storyline construction logic.
- `backend/src/chronos_vox/forecast/`: storyline heat index and forecasting adapters.
- `backend/src/chronos_vox/publish/`: `AnalysisState -> ForecastBundle` publishing logic.
- `backend/src/chronos_vox/contracts/` and `shared/contracts/`: shared data contracts. These are high-risk files.
- `shared/schemas/`: JSON schemas and validation artifacts.
- `shared/fixtures/`: golden fixtures, sample inputs, expected outputs, and test data.
- `frontend/workspace/src/loader/`: bundle loading and view-model mapping only.
- `frontend/workspace/src/forecast/`: real-time forecast model adapters used by the workspace.
- `artifacts/`: generated outputs, local analysis runs, and temporary exports. Do not treat as source of truth.
- `.venv/`: local environment only. Never edit or commit generated environment internals.

## Ownership And Parallel Work Rules

Parallel work is allowed only after shared contracts are stable.

Single-owner areas:

- `AGENT.md`
- shared contracts and schemas
- golden fixture bundle
- `storylineHeatIndex` definition
- LLM output schema for `Claim`, `Viewpoint`, and `Storyline` summaries

Recommended workstream split:

1. Normalization track
2. Claim extraction track
3. Aggregation and publishing track
4. Frontend workspace track

Each workstream should keep a disjoint write scope whenever possible.

Do not have two agents edit the same shared contract, fixture, or cross-cutting loader file at the same time.

If a task needs a shared-contract change:

1. Stop feature work.
2. Update the contract first.
3. Update the golden fixture.
4. Update validators and impacted tests.
5. Announce the change clearly in the PR summary.

## Engineering Conventions

### Core data rules

- Keep IDs stable and machine-generated.
- Every `Claim`, `Viewpoint`, and `Storyline` must be traceable back to source comments.
- Keep deterministic stages deterministic. Do not hide deterministic preprocessing inside LLM prompts.
- Keep the LLM boundary explicit and narrow.
- Prefer structured schemas over free-form text wherever machine consumption is required.

### LLM rules

- Use LLMs only for:
  - claim extraction from approved candidate spans
  - readable labels, titles, summaries, and explanations for stable `Viewpoint` and `Storyline` groups
- Do not use LLMs as the sole authority for core grouping or stable IDs.
- Cache repeated or near-duplicate inputs aggressively.
- Record audit metadata for every LLM-produced artifact.
- Always validate LLM output against schema before it enters the semantic pipeline.
- Design every LLM touchpoint with retry and fallback behavior.

### Backend rules

- Python is the default language for offline data processing.
- Split pure data transforms from IO and model-calling code.
- Make modules batch-friendly and deterministic where possible.
- Keep normalization, extraction, grouping, forecasting, and publishing as separate modules.

### Frontend rules

- The workspace consumes published data only.
- The loader may map, filter, or format fields, but must not infer core semantic entities.
- Keep a single shared focus model across views.
- Real-time forecast interaction operates on published storyline series, not raw comments.

### Documentation rules

- Record meaningful architecture changes in `docs/adr/`.
- Update plans when scope changes materially.
- Do not let code evolve silently away from the documented pipeline.

## PR Rules

Even before formal GitHub PRs exist, use these rules for every change bundle.

- One PR or change bundle per workstream-sized concern.
- Do not mix contract refactors, frontend polish, and pipeline logic in one change unless they are inseparable.
- Every PR must include:
  - summary of intent
  - exact files changed
  - risk level
  - verification performed
  - whether contracts changed
  - whether the golden fixture changed
- If UI changes are included, add screenshots or a short visual description.
- If contracts change, include a migration note and impacted areas.
- If LLM prompts or schemas change, mention expected quality or cost impact.

Recommended PR title prefixes:

- `contracts:`
- `normalize:`
- `claims:`
- `viewpoints:`
- `storylines:`
- `forecast:`
- `publish:`
- `frontend:`
- `docs:`

## Constraints

- Favor contract-first development.
- Favor deterministic preprocessing.
- Favor offline batch processing for heavy pipelines.
- Favor real-time forecasting only on precomputed storyline series.
- Favor fixture-driven validation.
- Favor small, reviewable changes over broad rewrites.

## Forbidden

- Do not change shared contracts casually.
- Do not let the frontend reconstruct `Claim`, `Viewpoint`, or `Storyline` from raw comments.
- Do not commit raw large datasets unless explicitly approved and documented.
- Do not commit secrets, tokens, API keys, or provider credentials.
- Do not edit `.venv/` contents manually.
- Do not replace deterministic preprocessing with prompt-only logic.
- Do not let LLMs assign final structural grouping without deterministic support.
- Do not introduce vendor-locked LLM logic into core domain types.
- Do not use destructive Git commands to discard others' work.
- Do not silently change `storylineHeatIndex` semantics.

## Definition Of Done

A task is done only when all applicable items below are true.

- The change stays inside its agreed write scope.
- Contracts remain valid, or all dependent artifacts are updated together.
- New behavior is documented where needed.
- Verification is run and recorded.
- No source-of-truth conflict remains unresolved.
- For pipeline work, outputs remain traceable to inputs.
- For LLM work, schema validation and audit behavior are covered.
- For frontend work, bundle consumption still matches published contracts.

## Acceptance And Validation

Use the checklist below before handing work to another agent or reviewer.

### Contract changes

- contract file updated
- JSON schema updated if applicable
- golden fixture updated
- contract consumers updated
- breaking-change note written

### Normalization changes

- raw-to-normalized transform is deterministic
- duplicate and noise handling are verified
- time normalization is verified
- quality or source classification changes are documented

### Claim extraction changes

- candidate span generation is explained
- LLM schema is enforced
- retry, cache, and failure handling are covered
- low-confidence or invalid outputs are isolated, not silently accepted

### Viewpoint or Storyline changes

- structural grouping remains deterministic or explainably rule-based
- LLM-generated display text is separated from structural identity
- traceability from storyline to source comments still works

### Forecast changes

- only future segments change
- historical segments remain untouched
- `storylineHeatIndex` assumptions are documented
- model-switch behavior is verified

### Frontend changes

- uses published bundle only
- shared focus state still works across views
- no loader-side semantic reconstruction is added
- visual or interaction changes are described and validated
