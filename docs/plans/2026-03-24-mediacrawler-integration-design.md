# MediaCrawler 到 Chronos-Vox 全链路对接设计文档

日期：2026-03-24

## 1. 文档目标

本文档定义 `MediaCrawler -> Chronos-Vox` 的全链路对接方案，目标是把“关键词发起采集”升级成可直接进入主工作台的稳定流程。

默认前提已经锁定：
- `MediaCrawler` 视为外部采集服务
- 默认用户体验是一键全链路
- 主项目只依赖稳定输入协议，不依赖爬虫内部实现细节
- 最终结果落点仍是现有统一工作台，而不是独立结果页

本文档不绑定具体语言、队列、数据库或部署形态，重点定义边界、状态流、最小接口和恢复策略。

## 2. 系统定位与边界

全链路包含四个角色：

1. `MediaCrawler`
   负责接收采集任务、执行跨平台抓取、输出原始评论结果和任务元数据。

2. `中间数据层`
   负责把采集结果转成主项目可消费的标准输入，包括清洗、去重、字段映射、批次归档和结果清单。

3. `chronos-vox-runtime`
   负责将标准化评论转成：
   `评论 -> Claim -> Viewpoint -> Storyline -> Forecast`
   并生成工作台使用的分析产物。

4. `前端工作台`
   负责发起任务、查看任务状态、进入统一工作台并浏览：
   - 主线
   - 关系
   - 证据

边界原则：
- `MediaCrawler` 是外部能力，不并入主项目核心仓库结构
- 主项目只消费结构化任务状态和标准结果文件
- 爬虫内部平台适配、登录、限流、重试细节都留在 `MediaCrawler`
- Chronos-Vox 只关心“任务是否完成、结果在哪里、格式是否合规”

这样做的原因是：
- 降低爬虫实现对主工作台的耦合
- 允许未来替换不同采集器而不改分析主链
- 让前端和 runtime 面向稳定任务契约开发

## 3. 一键全链路目标体验

用户在网站中输入：
- 关键词
- 时间范围
- 平台范围

然后系统自动完成：

`创建采集任务 -> 抓取 -> 结果落地 -> 标准化 -> 分析 -> 打开工作台`

用户体验要求：
- 用户无需手动分步切换到“导入”和“分析”页面
- 系统在同一工作流里展示任务进度
- 任务完成后自动进入对应工作台结果
- 如果已有可复用结果，则自动跳过重复环节

### 3.1 标准任务状态机

任务状态机统一为：
- `待启动`
- `抓取中`
- `抓取完成`
- `清洗中`
- `分析中`
- `可查看`
- `失败`

可补充的子状态信息：
- 当前平台
- 已抓取条数
- 最近更新时间
- 失败原因摘要
- 是否使用缓存结果

### 3.2 用户侧流程

1. 用户输入关键词并点击开始
2. 系统创建 `CrawlTask`
3. 前端展示统一进度卡片
4. `MediaCrawler` 完成抓取并产出结果清单
5. 中间数据层将原始结果标准化为分析输入
6. `chronos-vox-runtime` 创建 `AnalysisJob`
7. 产出 `workspace_id`
8. 前端自动跳转或切换到该 `workspace_id` 对应的统一工作台

## 4. 核心对象与 ID 关系

文档中的关键概念对象如下。

### 4.1 CrawlTask

表示一次由用户触发或系统触发的采集任务。

建议字段：
- `task_id`
- `keyword`
- `platforms`
- `time_range`
- `requested_at`
- `status`
- `source`
- `latest_message`
- `result_manifest_uri`

### 4.2 CrawlTaskStatus

用于前端轮询或订阅显示。

建议字段：
- `task_id`
- `status`
- `progress_percent`
- `current_stage`
- `current_platform`
- `estimated_comment_count`
- `updated_at`
- `error_code`
- `error_message`

### 4.3 CrawlResultManifest

表示一次采集任务的结果总清单，是中间层和 runtime 的交接物。

建议字段：
- `task_id`
- `dataset_id`
- `keyword`
- `platforms`
- `time_range`
- `raw_record_count`
- `output_files`
- `schema_version`
- `created_at`

### 4.4 NormalizedCommentBatch

表示标准化后的评论批次。

建议字段：
- `dataset_id`
- `batch_id`
- `schema_version`
- `comment_count`
- `platform_breakdown`
- `language`
- `file_uri`

### 4.5 AnalysisJob

表示一次运行 `chronos-vox-runtime` 的分析任务。

建议字段：
- `analysis_id`
- `dataset_id`
- `status`
- `artifact_manifest_uri`
- `started_at`
- `completed_at`
- `error_message`

### 4.6 WorkspaceSession

表示前端可直接进入的结果工作台会话。

建议字段：
- `workspace_id`
- `analysis_id`
- `bundle_uri`
- `default_primary_view`
- `created_at`

### 4.7 ID 传递关系

主链 ID 关系固定为：

`task_id -> dataset_id -> analysis_id -> workspace_id`

含义是：
- `task_id` 标识一次采集任务
- `dataset_id` 标识一次可复用的数据集结果
- `analysis_id` 标识一次分析运行
- `workspace_id` 标识一次前端可打开的工作台结果入口

## 5. 数据接口与交付契约

### 5.1 MediaCrawler 对外最小交付物

`MediaCrawler` 不需要暴露内部抓取细节，但至少需要交付：

1. 任务元数据
   - 关键词
   - 平台
   - 时间范围
   - 启动时间
   - 状态

2. 原始评论记录
   - 原始文本
   - 发布时间
   - 平台来源
   - 作者或匿名标识
   - 原始 URL 或内容来源标识

3. 结果清单
   - 结果文件路径或 URI
   - 记录条数
   - schema 版本
   - 是否完整完成

### 5.2 中间层标准化产物

中间层负责把抓取结果变成主项目稳定输入。

标准化必须完成：
- 字段统一
- 文本清洗
- 时间格式统一
- 平台名称统一
- 去重
- 无效记录过滤
- 批次切分与清单生成

最终目标是让 runtime 只读取 `NormalizedCommentBatch`，不直接依赖某个平台的原始字段。

### 5.3 主项目需要的最小任务接口

主项目对接时只依赖以下最小能力：

1. 创建采集任务
2. 查询任务状态
3. 获取采集结果清单
4. 触发分析任务
5. 查询分析状态
6. 查询工作台入口

可以抽象成以下概念接口：

- `create_crawl_task`
- `get_crawl_task_status`
- `get_crawl_result_manifest`
- `start_analysis_job`
- `get_analysis_job_status`
- `get_workspace_session`

## 6. 前端映射与工作台联动

### 6.1 入口位置

前端应在统一工作台外壳中提供“关键词发起采集”入口，而不是跳出到另一套后台系统。

建议入口形态：
- 顶部全局入口
- 首页空态入口
- 最近任务列表入口

### 6.2 任务列表与状态提示

任务列表至少展示：
- 关键词
- 平台
- 时间范围
- 当前状态
- 最近更新时间
- 是否可查看
- 是否可恢复

失败提示至少展示：
- 失败发生在哪个阶段
- 是否有部分结果可用
- 是否可重试
- 是否可直接复用历史结果

### 6.3 与统一工作台的衔接

一键链路完成后，前端不跳独立结果页，而是直接进入统一工作台。

进入规则：
- 默认主视图仍是 `主线`
- 若任务刚完成，可在状态带中提示“这是最新采集结果”
- 如为复用任务，则提示“已复用已有采集/分析结果”

工作台中仍使用现有三镜头：
- `主线`
- `关系`
- `证据`

不新增第二套结果浏览器。

## 7. 失败、缓存与恢复策略

### 7.1 抓取失败

若 `MediaCrawler` 抓取失败：
- 记录失败阶段与平台
- 若已有部分平台结果，则允许进入“部分结果模式”
- 若无有效结果，则停留在任务页并提供重试

### 7.2 数据为空

若抓取成功但有效评论为空：
- 任务可结束为“可查看”
- 但工作台展示为空结果页
- 明确提示可能原因：关键词过窄、时间范围过短、平台无命中

### 7.3 分析失败

若标准化成功但分析失败：
- 保留 `dataset_id`
- 允许重新触发分析
- 前端不丢失任务上下文

### 7.4 缓存与复用

复用原则：
- 相同关键词、相同平台、相同时间范围可优先查询已有 `dataset_id`
- 若已有标准化结果，则跳过抓取
- 若已有成功 `analysis_id`，则跳过重复分析
- 前端需要明确提示“本次使用了复用结果”

### 7.5 最小可用恢复链路

系统至少支持：
- 已有抓取结果时跳过采集
- 已有标准化结果时跳过清洗
- 已有分析结果时直接进入工作台

## 9. 三个验收场景

### 场景一：首次跑通

用户输入新关键词后：
- 成功创建采集任务
- 能持续看到状态变化
- 采集和分析完成后自动进入工作台
- 能在工作台中看到对应 `主线 / 关系 / 证据`

### 场景二：结果复用

用户再次输入相同条件时：
- 系统优先命中已有 `dataset_id`
- 如已有分析结果，直接返回 `workspace_id`
- 页面明确提示已复用结果
- 用户无需等待整条链路重跑

### 场景三：部分失败

某个平台抓取失败但其他平台成功时：
- 任务不直接整体报废
- 用户能看到“部分平台失败”的状态
- 仍可进入部分结果工作台
- 系统提供恢复或补跑入口

## 10. 实现优先级建议

建议按以下顺序落地：

1. 先打通任务状态流和最小结果契约
2. 再实现标准化结果到 runtime 的接入
3. 再接前端一键入口与状态页
4. 最后补缓存复用、补跑与部分结果模式

这样可以先验证主链能跑通，再逐步增强恢复能力与用户体验。

## 11. 验收标准

完成后应满足：
- 用户可以从关键词输入直接进入工作台
- 主项目不依赖爬虫内部实现细节
- 采集、标准化、分析、工作台四段状态清晰可追踪
- 失败时用户知道失败在哪、能否恢复、能否复用
- 同条件任务可命中缓存，避免重复抓取和重复分析
